# Dots 주간 X 사용자 ID 경로 점검

이 문서는 Dots에 등록할 주간 작업의 실행 지침입니다. 여기 적힌 내용만으로 자동화가 등록되지는 않습니다.

## 등록 전 확인

1. 먼저 Dots의 기존 작업과 일정을 확인합니다. 같은 공개 프로필의 ID 경로를 같은 주기로 확인하는 작업이 있으면 새 일정을 만들지 말고 기존 작업을 재사용하거나 갱신합니다.
2. 이 점검의 공개 기준 프로필은 `https://x.com/X`와 `https://x.com/Google`입니다. 경로 건강성 확인용으로 명시해 선택한 표본이며, 실제 사용자나 내부 기준 ID를 추정하지 않습니다. 숫자 사용자 ID는 매 실행에서 페이지 데이터로부터 동적으로 확인합니다.
3. 일정을 만들기 전에 Dots 자체 클라우드 브라우저가 열리고 두 공개 프로필에 접근할 수 있는지 확인합니다. 각 페이지에서 `tools/probe-x-user-id.js`의 전체 표현식을 실제 X 페이지 개발자 콘솔의 **MAIN world**에서 한 번 실행해 smoke run을 기록합니다. 반환값은 JSON 문자열이어야 합니다.
4. 클라우드 브라우저나 MAIN-world 콘솔을 사용할 수 없거나 초기 smoke run을 마칠 수 없으면 일정을 성공으로 등록하지 말고 차단 사유를 기록합니다. 로컬 브라우저나 Codex 로컬 자동화로 조용히 대체하지 않습니다. 로컬 대안은 사용자가 별도로 허용한 경우에만 논의합니다.

## 일정

- 매주 월요일 10:00, `Asia/Seoul`
- 실행 환경: Dots 자체 클라우드 브라우저
- 대상: 공개 기준 프로필 `https://x.com/X`, `https://x.com/Google`
- 코드: 저장소의 `tools/probe-x-user-id.js`에 있는 단일 JavaScript 표현식

## 매회 실행

1. Dots 클라우드 브라우저에서 `https://x.com/X`와 `https://x.com/Google`을 각각 엽니다. 페이지 URL이 `https://x.com/<handle>` 또는 `https://twitter.com/<handle>` 공개 프로필 경로인지 확인합니다.
2. 프로브 표현식 전체를 각 페이지의 MAIN-world 개발자 콘솔에서 그대로 실행합니다. 결과가 없거나 콘솔이 다른 실행 영역에 있는 경우에는 조사 결과를 만들지 말고 접근 실패로 기록합니다.
3. 결과의 `status`, `reference.status`, 최대 세 개 `samples`의 `postId`, `userId`, `status`, `path`만 작업 기록에 남깁니다. 프로브가 반환하지 않은 값은 추정하지 않습니다.
4. `ok`는 그 주에 실제 게시물을 검사해 DOM 게시물 ID와 React 작성자 ID가 일치했을 때만 기록합니다. `no_posts`, `login_required`, `browser_unavailable`, `probe_error`는 검사를 마친 성공으로 표시하지 않습니다.
5. 첫 성공 실행에서 각 프로필의 작성자 `userId`를 동적으로 읽어 Dots 작업 기록의 기준값으로 삼고, 다음 실행부터 새 표본과 비교합니다. 코드나 지침에 기대 숫자 ID를 고정하지 않습니다. 새 게시물의 `postId`는 매번 달라지므로 이전 실행의 게시물 ID와 비교하지 않습니다.
6. React 경로의 깊이는 관측 증거입니다. React 내부 경로 계약으로 간주하지 않습니다. 경로 깊이만 달라지고 작성자 ID가 계속 검증되는 경우에는 기록만 갱신하며 스키마 변경으로 알리지 않습니다.

## 알림 기준

- 정상 결과와 변화가 없는 결과는 작업 기록에 조용히 남기고 사용자에게 알리지 않습니다.
- 새로 `react_fiber_missing`, `tweet_model_missing`, `tweet_id_mismatch`, `user_id_missing`, `identity_conflict`, `reference_conflict`, `fiber_bound_reached` 등 ID 검증을 깨뜨리는 경로를 만나면 한 번 알립니다. 관측된 상태와 `path`를 함께 전달하고, 실제 ID를 찾지 못했다면 그 사실을 분명히 씁니다. 깊이 제한에 닿아 검증하지 못한 표본은 성공이 아닙니다.
- 검증된 작성자 ID가 해당 프로필의 이전 성공 기록과 달라지면 새 ID 경로 변화로 한 번 알립니다. 확인 전에는 기존 기준값을 자동으로 교체하지 않습니다.
- `reference.status: "unavailable"`은 같은 핸들의 JSON-LD 참조 ID를 얻지 못했다는 뜻입니다. 이것만으로 React 경로 변경이나 스키마 드리프트라고 판단하지 않습니다. 안전하지 않은 숫자 또는 상충하는 JSON-LD 값도 구분해서 기록합니다.
- 로그인 필요, 브라우저 접근 실패, 페이지 미로딩, 게시물 부재는 운영 접근 상태로 기록합니다. 그 자체를 X 스키마 변경으로 보고하지 않습니다. 같은 접근 차단이 두 번 연속 주간 실행에서 반복되어 사용자 조치가 필요할 때만 한 번 알립니다.
- 이미 알린 동일한 실패가 그대로 이어지면 반복 알림을 보내지 않습니다. 원인이 해결된 뒤 다시 실패하거나, 새롭고 조치가 필요한 ID 경로 문제가 나타난 경우에만 다시 알립니다.
- 한 주에 실제 프로브를 실행하지 못했다면 그 주를 성공으로 채우지 않습니다. `미검사`와 이유를 남깁니다.
- 소스 수정, 자동 수정, 릴리스, 배포는 수행하지 않습니다. 필요한 변경은 근거와 함께 별도로 보고합니다.

## 기대되는 검사 범위와 한계

프로브와 확장 프로그램은 각각 React fiber 노드 최대 64개(시작 노드 깊이 0부터 깊이 63까지)를 확인합니다. 프로브는 공개 프로필 페이지의 작성자 헤더와 게시 시각 링크를 기준으로 현재 렌더링된 작성자 게시물 최대 세 개를 살핍니다. 각 게시물에서 DOM의 `/handle/status/<digits>` ID와 일치하는 React `memoizedProps.tweet.id_str`를 찾은 뒤 문자열 `tweet.user.id_str`을 확인합니다. `path`에는 런타임 suffix를 감춘 경로와 관측 깊이가 기록됩니다. 인용, 소셜 컨텍스트, 일반 링크 카드의 작성자는 표본에 넣지 않습니다.

출력에는 시간, 공개 경로, 요약·상태, 프로필 JSON-LD 참조 상태와 게시물 ID 표본만 포함됩니다. 게시물 본문, 프로필 소개, 쿠키, 인증 헤더, 메시지, 비공개 피드, 전역 앱 상태는 읽거나 기록하지 않습니다. 네트워크 응답 가로채기, X API 호출, 페이지 콜백 실행, React 수정도 하지 않습니다.

프로브는 현재 보이는 DOM과 제한된 React `return` 조상만 확인합니다. 게시물이 없거나 페이지에 접근할 수 없는 주에는 내부 경로를 검사하지 못하므로, 그 결과로 구조가 정상이라고 결론 내릴 수 없습니다.
