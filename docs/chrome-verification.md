## 타임라인 표시의 확인된 입력 구조

공개 X 프로필의 게시물에서 아래 구조를 확인했습니다.

- 게시물: `article[data-testid="tweet"]`
- 본문 작성자 헤더: `[data-testid="User-Name"]`
- 작성자 링크: `/<handle>`이며, 별도의 게시 시각 링크는 `/<handle>/status/<post ID>`입니다.
- 검사한 게시물에는 `[data-user-id]`가 없습니다.

0.2.0에서는 검증된 프로필에서 얻은 ID와 핸들 연결 정보로 타임라인 작성자를 찾았습니다. 아래 0.3.0부터는 이 연결 방식을 사용하지 않고 게시물의 React 데이터에서 숫자 작성자 ID를 직접 확인합니다.

## 0.2.0 — 2026-10-27

같은 Chrome에서 확장 프로그램을 `0.2.0`으로 다시 로드하고, X 페이지 자체도 새로고침한 뒤 확인했습니다. 실제 팝업과 `chrome.storage.local`을 사용했으며, 게시물 DOM이나 저장소 응답을 테스트용으로 대체하지 않았습니다.

| 확인 항목 | 결과 |
| --- | --- |
| 프로필에서 저장한 메모를 게시물 작성자 아래 표시 | 통과, 처음 확인한 게시물 10곳에 표시 |
| 스크롤 후 새로 나타난 게시물에도 적용 | 통과 |
| 팝업 수정 후 타임라인의 기존 메모 갱신 | 통과, 표시된 14곳 갱신·이전 문구 제거 |
| 삭제 후 프로필·타임라인 표시 제거 | 통과, 메모 표시 0곳 |
| 실제 홈 게시물 작성자의 프로필 방문·저장 후 홈으로 복귀 | 통과, 해당 홈 게시물에 메모 표시 |
| 해당 메모 삭제 후 홈으로 복귀 | 통과, 테스트 문구 제거 |

테스트 메모는 모두 삭제했고, 확인용으로 연 탭도 닫았습니다. 기존 스토어판의 설정과 저장소는 변경하지 않았습니다. 개발 확장은 로드된 상태입니다.

이전 숫자 ID 메모의 연결, 핸들 변경·재사용, 동시 저장, 인용·멘션 구분, DOM 재사용과 저장 오류는 jsdom/확장 API 모의 회귀 테스트로 별도 검증했습니다. 기존 숫자 ID만 가진 메모를 실제 Chrome 저장소에 직접 주입하는 검증은 수행하지 않았습니다.

## 0.3.0 — 2026-10-28

같은 Chrome에서 정식 checkout의 개발 확장을 다시 로드하고 실제 X 페이지를 새로고침했습니다. 프로필 팝업과 실제 확장 저장소로 검증했으며, 기존 사용자 메모는 보존하고 이 검증에서 만든 임시 메모만 삭제했습니다. 기존 비활성 스토어판은 변경하지 않았습니다.

| 확인 항목 | 결과 |
| --- | --- |
| Chrome 확장 상세에 버전 0.3.0 표시 | 통과 |
| 프로필에서 숫자 ID별 메모 저장·새로고침 후 유지 | 통과 |
| React 게시물 ID와 DOM 게시 시각 링크의 ID 비교 | 통과, 작성자 ID는 문자열이며 일치한 React 모델의 `tweet.user.id_str`에서 읽음 |
| 프로필 타임라인의 본문 작성자 아래 메모 표시 | 통과, 스크롤 후 6곳에서 표시 확인 |
| 팝업 수정 즉시 기존 타임라인 메모 갱신 | 통과, 6곳에서 새 문구 확인 |
| 프로필 정보가 없는 검색 타임라인에서 기존 메모 표시 | 통과, `from:X` 최신 검색 결과 9곳에서 표시 확인 |
| 임시 메모 삭제 후 표시 제거·다른 기존 메모 보존 | 통과 |

실제 X의 게시 시각 `<a>`에도 `role="link"`가 있었습니다. 후보 링크 자체는 허용하고, 후보를 감싼 인용 카드의 `role="link"`는 제외하도록 수정했습니다. 서로 다른 게시물·작성자 ID와 인용 카드를 포함한 회귀 테스트로 두 실행 영역을 함께 확인했습니다.

핸들 변경·재사용, 숫자 정밀도, ID 불일치·누락, 메시지 검증, 64개 fiber 탐색 제한, DOM 재사용·저장소 변경은 자동 테스트로 확인했습니다. 실제 계정의 핸들 변경이나 X의 React 데이터 수정은 수행하지 않았습니다. Dots 클라우드에서의 최초 프로브 실행과 주간 일정 등록은 별도 설정 단계이며, 이 로컬 Chrome 검증으로 대신하지 않습니다.
